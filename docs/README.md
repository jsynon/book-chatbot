# Reading Companion architecture and development guide

The Antilogicalism Reading Companion helps readers move from a question to relevant passages in the library and back to the original books. The public site is a pilot for accurate, question-aware answers with citations. Treat answers as guides to reading: valid page links and model review do not guarantee that every claim is correct or complete.

Use the [live Reading Companion](https://jsynon.github.io/antilogicalism/reading-companion/) to ask a question, inspect cited passages, open the original PDF page, and continue with a follow-up.

## The three repositories

| Repository | Responsibility |
| --- | --- |
| [antilogicalism](https://github.com/jsynon/antilogicalism) | Static website, Bookshelf, Library Search, Reading Companion interface, and live evaluation workflows. |
| [antilogicalism-library-data](https://github.com/jsynon/antilogicalism-library-data) | Published catalog and v48 search data, extracted book pages, source fingerprints, and original PDF metadata. |
| [book-chatbot](https://github.com/jsynon/book-chatbot) | Cloudflare Worker API for the public pilot and a separate Python/Ollama workbench for local development. |

The repositories share published catalog and book data. The Worker does not host a second copy of the full library. The public site and local workbench use different answer-generation implementations, so a local answer is not a direct test of the live Worker.

## Public answer path

The live interface is in `antilogicalism/reading-companion/`. Its search module reads the published library index, finds candidate pages, and tags pages with the question parts that led to them. It sends the selected page text and locations to the Worker; the browser does not decide which text is trusted.

The Worker path in `hosting-poc/public-gateway.mjs` and `hosting-poc/evidence-answer.mjs` works as follows:

1. **Plan the question.** The planner identifies the reader's intent, named works or authors, question parts, and focused search queries. A broad, single-author topic remains one required coverage part; distinct model search leads may still help retrieve examples or qualifications. Author-wide questions keep that author's available works unless the reader names a distinctive work phrase; an author's name appearing inside a book title does not count as naming that work. For a hypothetical response between two thinkers, the plan assigns source-side parts and searches to each author's own works, then adds a synthesis part linked to both. When selected-books mode skips planning, the Worker reconstructs that bounded structure only if the question explicitly names exactly two authors present in the verified source titles; groups follow the question's author order and retain two premise parts plus one shared inference part. Other selected-book questions keep the existing one-part fallback. Selected-book requests stay within their selected books.
2. **Retrieve and select pages.** The browser searches the published v48 data and selects a bounded set of passages. The shared index retriever recognizes only explicit, source-attested phrase equivalents (currently “dependent origination” and “dependent arising”); alternate wording is searched as one relevance concept, so the two words of the phrase do not count as separate evidence matches. This leaves the existing relevance threshold unchanged and does not add a model call. OCR index and publication pages are screened out of substantive evidence, including index scans where the folio and `INDEX` heading occur after several locator entries. If a planned side of a two-author comparison has no results while the other side does, the browser can make one local retry using the failed side's own query terms, the counterpart's successful query terms, and the reader question, restricted to the empty side's already planned book IDs. This adds no model call or page budget and leaves the side empty if it still finds nothing. Candidate merging reserves a returned eligible page for each question part when one exists before distributing additional pages across parts and works; this prevents a broad, multi-work part from filling the entire hydrated-candidate limit before another part receives evidence. If a part's exact wording was searched globally but a linked planner facet resolved the part to catalog works, retrieval also searches that wording inside the still-unsearched works. These scoped searches add no model call and use the same answer-page limit. In a one-part plan, a planner facet can link to the sole part when it shares one subject term after generic search wording is removed; multi-part plans retain the existing two-term matching rule. Each candidate records which question parts it may support. A part link is an eligibility hint, not proof that the passage supports an answer.
3. **Verify source text.** Before inference, the Worker checks each submitted page against published SHA-256 fingerprints and obtains canonical book, page, and PDF metadata. A mismatch is rejected. The verified page identity and PDF link come from the published data, not from model output. The answer and review inputs also carry credited-author, editor, translator, planner-role, explicit page-heading context, and title-guarded known work/page voice metadata. Those fields guide attribution but do not prove who speaks in an individual passage. When a known editorial-commentary page is cited, the citation preserves the commentator separately from the book's credited author.
4. **Compose by question part.** The composer receives the question parts and linked verified pages. It should answer each part directly in its first sentence, naming the requested concept or relation rather than relying on an unexplained pronoun-led opening. When asked what a phrase means, it should interpret the phrase before explaining its consequences. For comparisons, it should state each author’s position in a separate sentence using that author’s relevant evidence, then synthesize only a relationship supported by both sides. For a broad, single-part question, it should answer concisely in three to five sentences, treating planner search queries as retrieval leads rather than extra topics the reader asked to cover. Each factual sentence should make one main claim; the composer should not bundle distinct assertions into one sentence. It must distinguish authorial text from pseudonymous voice, quoted or reported speech, narration, editorial introductions, translator notes, and commentary. A credited book author or planner role is not automatically the speaker on a page. It cites the page IDs that support each sentence. Unsupported parts remain visible as gaps.
5. **Validate citations and review.** Deterministic checks reject unknown, out-of-scope, wrong-book, or wrong-part source IDs. Multiword text presented as a quotation is checked against a cited page; short single-word terms are treated as terminology. With review enabled, the existing second answer call assesses each cited sentence against exact spans from every cited source. Its compact input carries the part, claim, source IDs, claim-ranked span choices, and each page's planner source group. The reviewer must check the same concept, speaker, action, polarity, qualification, and scope—not topical overlap—and return one source decision for every cited source. It checks phrase-meaning answers for an explicit interpretation and checks each author premise against that author’s evidence; synthesis requires support for the specific relationship asserted. For each part, it must nominate the smallest set of direct-answer claims that covers the requested facets, not every claim by default. The reviewer now completes claim/source decisions before choosing that set; the Worker still requires every nominated claim to survive exact quote review. It removes rejected claims before final rendering; a rejected non-direct claim alone does not downgrade a part when the reviewer confirms the remaining answer is complete. A missing or rejected direct-answer claim, or an incomplete reviewer part decision, remains partial or unanswered. Review JSON may discard only a repeated closing delimiter that is structurally unmatched at that position, the exact syntax defect observed in paired run #9. The ordinary schema, claim IDs, source IDs, statuses, and exact spans are validated unchanged afterward; any other malformed or truncated output remains fail-closed with no retry call. The reviewer may select up to three spans per source and six per claim; the Worker validates every selected ID against fingerprint-verified text. A claim may drop a weak alternate citation only when review marked the claim answered, the remaining source has an accepted exact span, and every planner source group represented in the claim remains covered. Missing source decisions, missing spans, and unsupported required premises still keep the claim incomplete. The final answer and evidence map include only retained, reviewed claims and citations. A deterministic high-precision guard also rejects a directly matched capability claim when the selected passage explicitly says the speaker cannot do that action but the answer says they can. This catches clear polarity reversals; it is not a general semantic entailment check.

   Known title/page-guarded editorial pages must be attributed to the commentator or introduction; known pseudonymous work voices must be identified. An accepted, reviewed attribution can carry across later answer parts, but an unsupported claim cannot establish that context. Direct author pages do not inherit an editorial label. For a hypothetical answer about one author responding to another, the inference must be standalone and cautious, with relevant evidence for each author's premise and a narrow shared point of contact. It cannot be phrased as a historical judgment. Unknown, duplicate, or missing decisions and source spans remain incomplete. One supported clause does not validate a different clause in the same sentence. Composer and reviewer instructions suppress unrelated topic lists and retrieval-process narration. If review output is cut off, the trace reports `review-output-truncated` and the answer remains unverified without another model call. Model review remains fallible; exact citation and highlight locations do not prove semantic support.
6. **Return readable evidence.** The Worker groups up to three reviewer-approved excerpts per cited page and returns at most six distinct cited pages. Each excerpt retains its claim and question-part links; a legacy primary `quote` remains for compatibility. It ranks the primary excerpt using both its linked claim and the reader's question so a directly relevant phrase can lead over nearby context. This only reorders already reviewed, exact spans. The site matches the answer sentence before an inline citation to those claim points and opens the matching excerpt set in the page reader. The reader highlights every exact, unambiguous excerpt it locates and leaves unmatched text unhighlighted. The source card can show each approved excerpt for that page. Lexical ranking, OCR normalization, and exact substring matching do not establish semantic support; only reviewer-approved spans are eligible, and model review can still be wrong.

The public pilot uses the evidence pipeline unless `READER_PIPELINE=legacy` selects the rollback path. Public requests remain behind the Worker’s origin, Turnstile, visitor-rate, global-rate, and source-fingerprint checks. Full prompts, full source pages, and raw model responses are available only through the authenticated evaluation trace, not the ordinary public answer.

### Model calls

The Worker uses Cloudflare Workers AI with Gemma 4 26B A4B for answer composition and review. The planner is a separate call. A reviewed question normally uses one planning call, one composition call, and one review call. Compose-only skips review, so it uses one planning call and one composition call. The review is a fallible model judgment, not a truth certificate. Review output is bounded to 1,800 completion tokens; any truncation remains fail-closed and does not trigger a retry. Worker responses include the Cloudflare version ID and, when deployed with a 40-character Git SHA as the version tag, a validated `workerSourceRevision`. Deploy with the checked-out source SHA as the version tag. From the repository root in PowerShell, run `npx.cmd wrangler deploy --config .\hosting-poc\wrangler.public-pilot.jsonc --tag $sha`, where `$sha` is the 40-character SHA of the checked-out commit. Use the production config in your checkout; `wrangler.public.example.jsonc` is example-only. The live evaluator records the SHA in each case and the artifact's `workerSourceRevisions` list, independently of Cloudflare's deployment-generated version ID. A missing revision means the run cannot establish which Worker source was tested.

The authenticated review trace now records each claim/source handoff: a bounded answer-claim excerpt, candidate span IDs sent to the reviewer, IDs it returned, the exact source span retained by deterministic validation, and any validation reason. Part decisions also preserve the reviewer's original status separately from the final status after deterministic checks. When every composed answer sentence fails citation validation, the authenticated final trace summarizes the finite validation-reason codes; it does not add a model call or change the public failure response. Public highlights preserve the claim-to-quote relationship through the browser and bounded diagnostic summaries. This makes it possible to distinguish “the reviewer chose an unrelated span and the Worker accepted it” from “the reviewer chose valid evidence that still does not semantically support the claim.” The additional candidate and display grouping add no model call and do not expose the authenticated trace in public answers.

## Evaluation and quality limits

The website repository contains the live holdout and acceptance workflows. They report planner, retrieval, answer, and review progress while a run is underway. Authenticated runs can save the exact prompts, model outputs, source pages, rejection reasons, usage, and final answer for diagnosis. The saved answer audit also reports citation-to-highlight coverage and cited source IDs without a page-located highlight; this is diagnostic context, not a structural gate. In selected-books mode, part alignment remains restricted to the expected selected works. In all-books mode, the audit accepts another work only when it appears in that part's planner `sourceBookIds`, still requires the configured expected work, and reports additional eligible works separately for answer-quality review. That eligibility check does not establish semantic relevance.

Use the [evidence milestone release report](reader-evidence-milestone-release.md) for the project history, decisions, workflow findings, current fixes, and remaining validation. The seven-question development set is diagnostic; it is not evidence of general performance because it has informed changes. Reserve the unseen acceptance set for a frozen candidate.

The pipeline can still miss a passage because retrieval is limited and language in a question may differ from the book's wording. OCR damage can make a verified page hard to interpret. Fingerprints prove that submitted text matches the published page text; they do not prove that the OCR is correct or that a claim follows from the page. Model review can miss errors or downgrade supported prose. Structural tests check contracts such as source IDs, scope, and part links; they cannot establish philosophical, historical, or literary accuracy. Inspect cited passages whenever the interpretation matters.

## Code map

| Path | Purpose |
| --- | --- |
| `hosting-poc/public-gateway.mjs` | Worker routes, public pilot gates, page fingerprint verification, and response handling. |
| `hosting-poc/evidence-answer.mjs` | Question-part linking, composition and review prompts, citation checks, coverage status, and answer assembly. |
| `hosting-poc/reader-contract.mjs` | Worker planner, citation, and source contract, including separate editor and translator bylines. The website has a corresponding `antilogicalism/reading-companion/reader-contract.mjs`; keep shared behavior aligned when either copy changes. |
| `hosting-poc/*.test.mjs` | Offline Worker and pipeline regression tests. |
| `docs/reader-evidence-milestone-release.md` | Ongoing evidence and release record. |

Run the Worker checks from this repository:

```sh
node --test hosting-poc/*.test.mjs
```

Run browser search, interface, and evaluator checks from the `antilogicalism` repository:

```sh
node --test reading-companion/*.test.mjs
```

These suites use offline fixtures. They do not replace a live model run or source-based answer review.

## Separate local workbench

The repository also contains a Python application for local experimentation. It runs a local model through Ollama and does not call the Cloudflare Worker. On Windows, run `start.bat`; otherwise start it with `python app.py` and open `http://127.0.0.1:8765/`. Its developer view is at `http://127.0.0.1:8765/developer`.

For full-library local retrieval, the workbench needs local checkouts of `antilogicalism` and `antilogicalism-library-data` beside this repository. Follow the root [README](../README.md) for its setup. Local-model output tests the local pipeline only; use the website's authenticated workflow to test the public Worker.

**Guiding principle:** use AI to help readers find and understand the books while keeping the source text accessible and open to inspection.
